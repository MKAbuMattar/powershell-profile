# Coreutils Module

Detects, installs and manages [Microsoft coreutils](https://github.com/microsoft/coreutils), and
reports which command names it and this profile are both claiming.

## Why this exists

coreutils puts 78 GNU tools on Windows — `grep`, `head`, `tail`, `sort`, `wc` and the rest. This
profile also defines `grep`, `head`, `tail`, `touch` and `sed` as aliases for its own PowerShell
implementations.

PowerShell resolves an **Alias** before an **Application**, so the profile silently won every one
of those names. Typing `grep` ran `Get-ContentMatching`, which has different semantics, on a
machine where GNU grep was deliberately installed.

That is now a decision rather than an accident, with two halves:

- `PreferNativeTools` in [`profile.config.psd1`](../../profile.config.psd1) decides who wins.
- This module tells you what the current outcome actually is.

## Seeing the conflict

```powershell
Show-CoreutilsConflict
```

```
  cat        -> coreutils
  cp         -> Alias: cp
  grep       -> coreutils
  mkdir      -> Function: mkdir
  ...
```

With `PreferNativeTools = $true` (the default) most contested names go to coreutils. Three do not,
and cannot: `cp`, `echo` and `mkdir` are `AllScope` aliases or functions built into PowerShell
itself, which the loader is not able to remove. That is reported rather than silently accepted —
run the profile with `-Verbose` to see the loader say so.

## Changing who wins

There are three levers, in increasing order of bluntness:

| Want | Do |
| --- | --- |
| coreutils wins (default) | `PreferNativeTools = $true` |
| The profile's PowerShell implementations win | `PreferNativeTools = $false` |
| coreutils gives up a name entirely | `Disable-CoreutilsUtility find` |

The PowerShell implementations are always reachable by their full names — `Get-ContentMatching`,
`Get-FileHead`, `Get-FileTail`, `Set-FreshFile`, `Set-ContentMatching` — whichever way the aliases
resolve.

## Installing

```powershell
Install-Coreutils          # winget install --id Microsoft.Coreutils
```

Note that several winget packages match "coreutils". This installs `Microsoft.Coreutils`
specifically, which is the one providing `coreutils-manager` and the PowerShell integration this
module talks to. `uutils.coreutils` is a different project.

`setup.ps1 -Step Coreutils` does the same during installation, and it is included in
`-IncludeOptional`.

## The profile block

The coreutils installer appends a marked block to `Microsoft.PowerShell_profile.ps1` and records
the path under `HKLM:\SOFTWARE\Microsoft\coreutils\PowerShellProfiles`.

Both `Update-Profile` and `setup.ps1` preserve marked third-party blocks, so installing coreutils
after the profile — or the profile after coreutils — works either way round. Before that was
handled, updating the profile deleted the block while coreutils' registry entry still claimed the
shims were installed.

## Requirements

Enabling or disabling individual utilities writes to `HKLM`, so those two commands need an
elevated session. Everything else works unelevated.
